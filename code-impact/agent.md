# code-impact AGENT.md

> 이 폴더에서 작업하는 AI Agent(Codex, Claude 등)를 위한 작업 규칙.
> **루트 `AGENT.md` 규칙을 먼저 따르고**, 이 문서는 그 위에 code-impact 전용 규칙을 더한다.

---

## 0. 작업 시작 전 반드시 읽을 것 (이 순서로)

1. 루트 `AGENT.md` — 팀 공통 규칙 (브랜치, 커밋, 폴더 경계, 키 관리)
2. `code-impact/text.txt` — **원본 요구사항**. 무엇을 왜 만드는지. 기능 구현이 다 되면 `code-impact/text.txt` 파일을 삭제해주세요.
3. `code-impact/system_design.md` — 구조, 입출력 계약, 모듈별 책임, 테스트 기준

세 문서가 충돌하면: 루트 AGENT.md > text.txt > system_design.md 순으로 따르고, 충돌 사실을 보고한다.

---

## 1. 이 기능의 핵심 (구현 중 판단이 애매하면 여기로 돌아온다)

1. **입력은 커서 위에 단축키를 누를 때뿐.** 함수명 입력, 자연어 질문, 변경 예정 내용을 요구하는 기능을 만들지 않는다.
2. **호출자를 여러 단계, 여러 파일에 걸쳐 찾는다.** 직접 호출자에서 멈추지 않는다.
3. **호출 관계만으로 끝내지 않는다.** 호출자가 반환값·인자를 _실제로 어떻게 쓰는지_ 코드에서 확인한다.
4. **확인된 사실(`facts`)과 AI 추정(`risk`, `summary`)을 분리한다.** 이게 가장 중요하다.
5. **UI는 만들지 않는다.** 요약·상세 JSON만 반환한다.

---

## 2. 작업 범위

- 수정 가능: `code-impact/` 안의 파일만.
- 수정 금지: `extension/`, `copilot/`, `ai-slop/`, 루트 파일. 필요하면 코드를 고치지 말고 **이슈로 올릴 내용을 작성**해서 보고한다.
- `text.txt`는 요구사항 원본이다. **수정하지 않는다.**
- 요청받은 모듈만 구현한다. 다음 단계 모듈을 미리 만들거나, 요청에 없는 기능(캐시 서버, 설정 UI, 플러그인 구조 등)을 추가하지 않는다.

## 3. 하드 룰

### 출력

- stdout에는 **결과 JSON 하나만**. `print` 디버깅 금지, 로그는 `logging` → stderr.
- 출력 스키마는 `system_design.md` 3장을 정확히 따른다. 필드 추가·이름 변경·타입 변경 금지.
  - 바꿔야 하면 구현하지 말고 이유와 함께 보고한다. (바꾸게 되면 PR 제목에 `[양식 변경]`, extension 담당자 리뷰어 지정)
- 줄 번호: 입력은 0부터, 출력은 1부터.

### 사실과 추정 분리

- `facts`는 정적 분석(①~④)에서만 만든다. **LLM 출력을 `facts`에 넣지 않는다.**
- Usage Inspector(④)는 LLM을 호출하지 않는다.
- AI 문구에 단정 표현 금지: "반드시", "확실히 오류", "무조건 깨진다". → "확인해야 합니다", "영향을 줄 수 있습니다".

### 실패 처리

- AI가 실패해도 정적 분석 결과는 반환한다 (AI 필드 `null` + `warnings`).
- 예외를 삼키지 않는다. 사용자에게 보여줄 에러는 `system_design.md` 2.2의 에러 코드로만 낸다.

### 보안

- API key는 `.env`에서만 읽는다. 코드, 테스트, 로그, 에러 메시지, 커밋에 키를 쓰지 않는다.
- 새 환경변수가 생기면 `code-impact/.env.example`에 **이름만** 추가한다.
- 분석 대상 코드는 `--root` 밖을 읽지 않는다.

### 의존성

- 새 패키지는 표준 라이브러리로 안 될 때만 추가하고 `requirements.txt`에 버전 고정, 추가 이유를 보고한다.
- 허용된 기본 의존성: `tree-sitter`, `tree-sitter-language-pack`, `python-dotenv`, `pytest`, 선택한 모델 공급자 SDK 1개.

---

## 4. 코드 스타일

- Python 3.11+, 타입 힌트 사용, 모듈 간 데이터는 `models.py`의 dataclass로 주고받는다.
- 모듈 하나 = `system_design.md` 4장의 컴포넌트 하나. 파일 이름과 함수 시그니처를 문서와 맞춘다.
- 인터페이스·추상 클래스는 구현이 2개 이상일 때만 만든다. (예외: Model Adapter의 실제 모델/FakeModel)
- 주석은 "왜"만 쓴다. 의도적으로 단순하게 만든 곳은 한계를 주석으로 남긴다.
  예: `# 변수 추적은 같은 함수 내 한 단계까지만. 재할당 추적이 필요하면 여기 확장`

---

## 5. 테스트

- 실행: `cd code-impact && pytest`
- 기준 데이터: `system_design.md` 5장의 fixtures와 기대 결과표. **이 표가 정답지다.**
- 테스트에서 실제 LLM 호출 금지 → `FakeModel` 주입.
- 모듈을 구현하면 그 모듈 테스트를 같이 작성한다. 정상 케이스 + 경계 케이스(함수 밖 커서, 중첩 함수, 순환 호출, 동명 함수) 포함.
- 기존 테스트를 통과시키려고 테스트를 지우거나 기대값을 바꾸지 않는다. 기대값이 틀렸다고 판단되면 보고한다.

## 6. 완료 조건 (Definition of Done)

작업을 "완료"라고 하려면 아래를 모두 만족하고 **실제 결과를 보고**한다.

- [ ] `pytest` 전체 통과 (실행 명령과 출력 요약 첨부)
- [ ] 구현한 모듈이 `system_design.md`의 시그니처·책임과 일치
- [ ] (CLI가 연결된 이후) fixtures에 대해 실제 실행한 명령과 출력 JSON 첨부
  ```
  python -m code_impact analyze --root tests/fixtures --file tests/fixtures/price.js --line 2 --col 4
  ```
- [ ] `code-impact/` 밖 파일 변경 없음 (`git status`로 확인)
- [ ] 키·토큰이 코드나 로그에 없음

실행해 보지 않은 것은 "완료"가 아니라 "미확인"이라고 쓴다.

작업이 끝나면 아래 형식으로 보고한다.

```
## 한 일
- (변경한 파일과 요약)

## 확인 방법과 결과

- 결과:

## 못 한 것 / 한계
- (구현하지 않은 것, 알려진 한계, 문서와 다르게 판단한 부분)

## 다른 폴더에 필요한 것 (이슈 초안)
- (없으면 "없음")
```

## 8. Git

- 브랜치: `feature/code-impact-<기능>` (예: `feature/code-impact-resolver`), 버그는 `fix/code-impact-<내용>`
- 커밋: `<type>(code-impact): <요약>` — type은 `feat | fix | docs | refactor | test | chore`
- main에 직접 push 금지. PR + 리뷰 1명 이상 승인 후 merge.
- 요청받지 않았으면 커밋·push하지 않는다.
